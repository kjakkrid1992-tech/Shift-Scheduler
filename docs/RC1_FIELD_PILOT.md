# RC1 field pilot — parallel payroll, no live closure until signed off
Scope: five current staff identities, verified actual employment dates and compensation only. Existing EMP-TEST records are synthetic; never relabel them as real people or let them enter the real payroll roster. Separate test and pilot datasets. Use separate project or verified backup and reviewed cleanup/cutover; no blind delete, no invented dates. Keep old Excel/paper as source of truth during trial.
Suggested first complete payroll period 26 Nov–25 Dec 2026 if onboarding is ready; otherwise next complete period, or explicitly mark partial-period rehearsal and backfill verified records. Owner confirms code, department, employment dates, pay type/base/OT and eligibility. Manager confirms actual schedule, time and leave/off each day. No guessed time, statutory amounts or rates. Monthly staff not on a shift still require confirmed plan per department and verified daily attendance status for eligible dates before closure.
Day-to-day: manager prepares/maintains confirmed plan; records actual work after completed shift, bulk only for reviewed exact single-slot matches; manual exceptions, leave, off, and combined shifts; owner verifies approval queue. Record actual cash advance only once with evidence; shadow entry doesn't authorize payment. Compare with original logs daily/weekly. 
End of cycle: manager prepares itemized drafts for all five; compare normal/OT minutes, base and OT amounts, manual items, advances, tax/SSO, gross/deductions/net with Excel per person. Any unexplained difference blocks go-live. Leave final closure/payment untouched on actual records during shadow run; simulate closure, payouts, adjustments on disposable data only. Review current rates and legal deduction eligibility separately. Before go-live: verified full backup and restore, SQL regression evidence, role checks, real roster isolation, browser checks, owner sign-off. If a bug or mismatch, revert to Excel/paper for official payroll and retain issue evidence; don't retry blindly or delete records. Real financial use only in a later complete cycle after explicit sign-off. 
CI regression uses disposable PostgreSQL with a minimal auth.uid stub. It does not connect to Supabase or validate actual Auth/PostgREST/browser, backups, or company payroll rules. No production secrets or personal data in CI.
